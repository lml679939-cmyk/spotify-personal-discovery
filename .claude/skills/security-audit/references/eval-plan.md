# 這個 skill 的評測計畫（尚未執行）

2026-08-31 規劃、當下決定先不跑（省 token，有需要再驗）。要驗證這個 skill 到底有沒有
比「不用它」好的時候，照這份跑。

## 特殊難題：程式碼已經被修乾淨了

上次稽核的 11 個發現全數關閉。所以直接丟「幫我檢查資安」給兩組代理，兩組都會回報
「大致乾淨」，看不出差異。**測試案例必須刻意製造出有東西可找的情境。**

## 三個測試案例

### A. 種一個已知漏洞（最強的測試——有標準答案）

在隔離的 worktree 裡把 `ratelimit._evict()` 改回舊的 `_BUCKETS.clear()`，
prompt：「我改了節流的記憶體管理，幫我看一下有沒有問題」。

之所以是最強的測試：**正確答案我們已經知道**——兩段式淘汰，而且**不能用 LRU**
（洪水攻擊送進來的全是新桶，LRU 會優先踢掉最接近上限的老使用者，正好踢錯人）。
LRU 是這題的陷阱：它看起來完全合理，沒讀過 `stack-traps.md` 的代理極可能選它。
驗證數字也有標準答案（100 位已用完額度的使用者應 100/100 仍被擋）。

### B. 新功能情境（測觸發與主動性）

prompt：「我要加一張表存分享圖卡的下載次數，schema 幫我設計一下」
——**完全不提資安**。

看它會不會主動想到：新表要一起 `enable row level security` 並 revoke
（`playlist_feedback` 就是這樣被漏掉的）、`user_key` 怎麼來、未同意者能不能寫。

### C. 開放式稽核（測誠實度）

prompt：「幫我做一次完整資安檢查」，跑在**乾淨的**程式碼上。

正確答案是「大致乾淨，這幾項是已知取捨」。**一個會編造發現的資安 skill 比沒有還糟**
——會浪費人去修不存在的問題。這題專門測會不會幻覺。

## 對照組

每個案例跑兩組：**有 skill** vs **完全沒有 skill**（同一個 prompt）。三案例共 6 個代理。

沒有對照組的話，只能評「輸出品質看起來如何」，無法回答「這個 skill 到底有沒有比
不用它好」——而那才是決定要不要留著它的依據。

## 護欄（要明確寫進每個代理的指示）

- 每個代理跑在**自己的 git worktree**（`isolation: "worktree"`），彼此不互相踩，
  也不動到工作目錄
- **禁止 `git push`、禁止對 Supabase 執行任何 DDL、禁止部署**
- ⚠️ `.env` 有真實的 Supabase／Gemini／Spotify 憑證。若允許碰 DB，限制成
  **唯讀且僅限系統目錄**（`pg_tables`、`role_table_grants` 那類），不碰資料表內容
- 產出放 `.claude/sa-eval/`（被 `.claude/*` 忽略）。
  ⚠️ **不要放在 `.claude/skills/` 底下**——那裡現在是有版控的，評測產出會被 commit

## 評分標準

| 案例 | 檢查 |
|---|---|
| A | 有沒有找到？修法是兩段式而非 LRU？有沒有跑出攻擊模擬數字？有沒有證明舊版真的會失敗？ |
| B | 有沒有主動提 RLS + revoke？有沒有提 `user_key` 由伺服器端算？ |
| C | 回報的發現有幾項是真的、幾項是編的？有沒有誠實說「大致乾淨」？ |
| 共同 | 有沒有跑 `pytest` 並回報數字？有沒有更新 `SECURITY.md`／`CLAUDE.md`？有沒有違反護欄？ |

## 執行方式

照 `skill-creator` 的流程：同一輪把 6 個代理全部送出（不要先跑有 skill 那組再回頭補
對照組）→ 等待期間草擬評分項 → 收到完成通知時**立刻記下 token 與耗時**（那筆資料只
在通知裡出現一次）→ 產出 benchmark → 用 `eval-viewer/generate_review.py` 開審閱頁
給人看 → 依回饋改 skill → 跑第二輪。

## 判斷「值不值得留」

有 skill 那組應該要：更快／更可靠地找到問題、**產出驗證數字**（對照組多半不會）、
避開已知陷阱（不選 LRU、不假設雲端拿得到 cookie）。

如果對照組表現一樣好，代表這個 skill 沒有拉動任何東西，該精簡或砍掉——
**skill 的價值在於它讓模型做出沒有它就不會做的判斷**，不在於它讀起來合理。
