# 本專案的資安稽核與修補

## 這個 skill 存在的理由

2026-08-31 做過一次完整稽核，11 個發現全部修掉。過程中最貴的一課不是找漏洞，
而是**修好之後把正式站弄壞了**——因為「Streamlit Cloud 拿得到 XSRF cookie」這個
沒驗證過的假設被寫進了程式註解，而推翻它的證據其實早就在專案文件裡。

所以這個 skill 的重點不是「怎麼找漏洞」（那部分 `SECURITY.md` 已經寫好了），
而是**怎麼把發現變成真的有效、而且不會弄壞東西的修改**。

## 起手式：`SECURITY.md` 就是檢查依據

先讀專案根目錄的 `SECURITY.md`。它不是揭露政策而已，是一份威脅模型：資產清單、
角色、信任邊界、外部資料流、**10 條安全不變條件**、攻擊面對照表。

那 10 條不變條件是這次稽核的核心產出——**掃描時直接拿它們去對程式碼找違反處**，
比漫無目的地讀程式有效得多。例如第 1 條「身分只能由伺服器端決定」就直接對應到
「grep 所有 DB 查詢，確認 `user_key` 都是伺服器端算出來的」。

⚠️ 如果 `SECURITY.md` 的內容和程式碼對不上（例如提到已經不存在的端點、或漏掉新加的
資料表），**先修文件再開始掃描**。拿過時的威脅模型去掃描，會剛好略過最敏感的部分。

## 流程

### 1. 盤點：確認威脅模型仍然成立

對照 `SECURITY.md` 逐項確認，特別注意上次稽核之後的新增功能：

- 有沒有新的資料表？（→ 一定要一起開 RLS 並 revoke，見 `references/stack-traps.md`）
- 有沒有新的外部請求？（→ 資料裡帶來的網址一律要白名單）
- 有沒有新的使用者輸入欄位或身分機制？（→ 那是新的信任邊界穿越點）
- 有沒有新的祕密？（→ 補進資產清單，並確認沒進版控）

### 2. 掃描：跑 `references/sweeps.md` 的檢查

那份是這次稽核實際用過的指令，按面向分組（祕密、注入、XSS、SSRF、身分與授權、
節流、日誌、依賴）。每一組都附了「看到什麼算有問題」。

⚠️ **`.claude/worktrees/` 裡有舊版程式碼的副本**，被 gitignore 但全庫 grep 會撈到。
看到路徑在那底下的先確認，別拿舊版當現行程式改。

### 3. 排序：嚴重度是假設，不是結論

寫下發現時先給一個初判嚴重度，但**在驗證之前那只是假設**。

上次 HIGH-1（Supabase 沒開 RLS）我只看 DDL 就推論「anon key 一外流＝全站資料可讀寫刪」，
實際查下去發現 PostgREST 需要的四個權限 `anon` 一個都沒有，攻擊路徑本來就是斷的——
評級降為 Medium。**先驗證再定調，不然會把力氣花在錯的地方。**

### 4. 驗證：每個發現都要能重現

這是整套流程裡最重要的一步。`references/verify-recipes.md` 有這次用過的四種做法
（攻擊模擬、對真實 DB 的唯讀對照、把 JS 抽出來用 Node 實跑、本機重現雲端條件）。

兩條紀律：

- **證明測試不是空過的。** 寫完迴歸測試之後，把**舊版邏輯**也跑一次，確認它真的會失敗。
  上次 MED-6 就是這樣確認的：同一個以空金鑰偽造的 state，舊版接受（True）、新版拒絕（False）。
  一條「本來就會過」的測試等於沒有測試。
- **跟部署環境有關的判斷，要在部署環境上量過。** 本機跟 Streamlit Cloud 的差異大到會
  推翻結論（見 `references/stack-traps.md` 第一條）。量不到就想辦法在本機重現那個條件。

### 5. 修補：在最低層擋，讓不變條件無法被繞過

能在底層擋就不要在呼叫點加 `if`。例：`_sign_state()` 遇到空祕密直接拋
`_NoBrowserSecret`，而不是在 `get_login_url()` 檢查一次——這樣「用空金鑰簽章」在
**任何**程式路徑上都不可能發生，包括以後新增的呼叫點。

其他反覆用到的判斷：

- **fail closed，但要分清楚「還沒好」與「不可能好」。** 兩者混為一談的話，正常使用者
  會在首輪就被誤判。上次靠一個 `"unavailable"` 哨符把兩者分開。
- **淘汰／降級的順序本身可能是安全決策。** 節流桶滿了要丟哪一個？直覺的 LRU 是錯的
  ——洪水攻擊送進來的全是新桶，LRU 會優先踢掉最接近上限的老使用者，正好踢錯人。
- **修完要確認功能還在。** 資安修改最常見的失敗不是沒擋住，是把正常路徑也擋掉了。

### 6. 上線並在正式站確認

```bash
python -m pytest -q
```

然後照 `CLAUDE.md` 的部署規則走。**部署後一定要讀日誌**——上次的登入故障只在
Manage app 日誌裡看得到（`[AUTH]` 洗版），本機和測試都完全正常。

要 grep 的訊號：`[AUTH]`（OAuth 綁定失敗）、`[DB]`（持久化異常）、
`[GUEST]`（訪客身分解析，有出現代表正常）、`ImportError`／`NameError`。

## 收尾

- **改了行為就更新 `SECURITY.md` 與 `CLAUDE.md`。** 前者是下次掃描的依據，後者要寫
  「症狀 → 真正原因 → 量法」，不要只寫結論——這份文件的價值全在那些細節。
- commit 訊息把**驗證數字**寫進去（例如「10,800 次攻擊嘗試 → 400 次通過」）。
  沒有數字的資安修改，三個月後沒人知道它到底有沒有效。
